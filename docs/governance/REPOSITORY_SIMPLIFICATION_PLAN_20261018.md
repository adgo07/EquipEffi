# EquipEffi 软件梳理与去重实施方案

> 历史方案，已被 [2026-10-21 下一步方案](SIMPLIFICATION_NEXT_STEPS_20261021.md)收窄替代。下文保留当时设计，不再作为执行清单；新标准、Word、UI 美化暂缓，当前状态以 TASK_STATE 为准。

日期：2026-10-18。对象：单人使用 AI 开发、单人维护的 EquipEffi。

本方案承接[仓库检查报告](REPOSITORY_AUDIT_20261018.md)，纳入 Owner 本轮关于结果用语、变压器双文件和 UI 差异的补充。代码检查基线为 `master@2c7807f32ef08d18554014328efd4ceaa356726f`；仓库默认分支实际为 `master`。本文件是后续实施方案，本轮只补充规范与方案文档，不宣称生产代码已经整改，也不自动改变标准支持或历史 Phase 验收状态。

## 一、方案结论与本轮边界

**保留现有分层和离心泵已验证计算链，将重复的业务定义、公共流程和输出解释逐步收拢；每接通一条公共路径，同时退出对应旧路径。** 目标是修改一项业务规则只需修改其权威依据和对应实现，各交付端随之获得一致行为，不以减少多少文件或代码行为验收目标。

当前只有 GB 19762—2025 离心泵映射可用。其余标准，包括变压器，仍在核实验证；已有文件、运行包、历史冻结和已合并 PR 均不自动代表本轮核实完成。前四个工作包可围绕离心泵和已有通用结构展开，真实第二标准接入须等该标准核实完成、Owner 明确确认可用并按既有开发流程推进。

以下已确定，不再作为每次普通重构的重复询问事项：

1. 经批准的标准映射、配套已核验表值和明确的软件决定，构成核心业务依据；标准原文事实、异常、技术判断与软件决定分别如实记录。
2. 业务结果显示统一；通用结果名称只在[标准档案规范](../standards/README.md)维护。显示统一不改变标准的公式、适用性、缺失语义、比较方向或等级合并规则。
3. 一套核心依据可以有多个互补文件。变压器的主映射 Markdown 与 35 表人工校对工作簿是两个核心文件，共同使用和保护。
4. GUI、Excel、Word、API 及未来客户端复用同一正式业务定义和分析结果；界面与文件格式保留各自必要的布局。
5. 新建分析的业务表单允许按标准不同；首页、标准库、记录、设置、导入流程和结果展示尽量使用公共骨架，并与青舟产品家族保持一致。
6. 核心算法与平台、文件格式、数据库和 UI 分离。当前整理不要求重写语言、实现全部平台或提前制造复杂插件系统。

用户本地 G: 工作树、未跟踪资料、临时目录和第三方报告中的文件数量问题，由用户指定的第三方核实。相关意见作为整理线索吸收，本方案不将其作为已验证删除依据，也不以完成整盘清理作为公共代码整改的前置条件。

## 二、统一结果用语，同时保留真实判定语义

### 2.1 当前三级能效体系的显示口径

下表用于说明本轮迁移，长期规范以标准档案入口为准。名称确定后，AI 不得自行换同义词；后续确需改变，由 Owner 明确决定并在原入口留痕。

| 用户看到的结果 | 使用条件 | 当前离心泵需要处理的旧显示 |
|---|---|---|
| 1级、2级、3级 | 按本标准及已确认映射，能够确定对应等级 | 保持既有名称 |
| 未达3级 | 已有充分依据，明确未达到该标准的 3 级要求 | 原“未达标”统一至此 |
| 不在范围 | 有明确证据证明不属于所选标准适用范围 | 范围结果原“不适用”统一至此 |
| 无法判定 | 当前依据不足，或必要类别、分支等尚未确定 | 原“无法判定”保留；不确定类别原“无法评价”统一至此 |

“不在范围”附范围依据，“无法判定”附缺失项或未确认原因。原因从共享结果的 `issue_codes`、`missing_fields`、`explanation` 等字段形成，GUI、Excel、Word 不各写一套业务解释。[依据 S2]

### 2.2 不能压成六个状态枚举

六种显示名称不是六种底层状态。继续分别保留等级、评价状态、原因、软件支持状态、执行/保存状态和记录资格：

- 当前泵的低于最低等级是 `SUCCESS + BELOW_MINIMUM`，属于有效判定；不能改成计算失败。
- 当前资料不足可以形成合法业务终态及单台记录；明确选择“不确定类别”虽然也显示“无法判定”，目前仍不可形成单台 Record，批量结果保留该行。改显示名称不改变这项差别。
- 对正式评价返回 `INVALID_INPUT` 的请求，就近说明错误原因，不得形成正式单台记录；界面校验不得改变各标准已批准的输入问题与范围判定顺序，不能把该错误状态包装成一条合法的“无法判定”记录。
- 标准包读取失败或执行异常属于系统失败；保存失败应保留已得到的业务结果并提示保存失败。两者不能改写能效等级。
- 软件“当前未支持”属于能力边界，不能显示成标准“不在范围”。所选标准尚未实施、已废止或被替代，继续按已有规则作非阻断日期提醒。

具体判断顺序由各标准映射决定。例如，泵在类别已识别且有效流量足以证明范围外时，即使部分其他输入缺失或非法，且不影响该项范围依据，也可能正确返回范围外；不能新增“只要缺参数就一律无法判定”的全局规则，也不能用统一表单拦截改变这一先后关系。[依据 S2、S3]

本轮不全文替换原标准、冻结映射、历史快照、输入选项中的“不适用”等文字。现有 `PUMP_NUMERIC_AND_DECISION_CONTRACT_V2.md` 及历史 Phase 文档中的旧展示表保留历史意义；当前展示约定由标准档案规范明确覆盖。实施时修改实际显示入口及其直接说明，保留原始证据。未来若有四级、五级或非三级体系，应如实承载其结构，不能为套用当前界面而删等级或制造 3 级阈值。

### 2.3 具体代码落点

现有 Qt 与 Excel 已共用泵服务中的 `user_conclusion_text()`，从这个真实入口扩展，再迁出为轻量公共结果投影；不另造并行的中文状态库。共享投影依据结构化状态与等级生成名称，适配器只排版。Qt 新建页和记录页直接输出 `grade` 的位置也接入该投影，防止 `BELOW_MINIMUM` 进入普通界面。[依据 S2、S4]

## 三、把“一套来源”落实到文件和运行时

### 3.1 一套批准依据可以由多个文件组成

每个标准版本只有一个档案入口，由其 README 指明当前共同使用的文件、修订号、核实范围及证据。正文各维护一处，入口可以有链接，不能出现两套分别编辑的“最终版”。

| 内容 | 唯一维护位置与处理方式 |
|---|---|
| 原标准事实、异常原貌 | 原文证据及定位；映射如实记录，不静默修正 |
| 适用范围、选表选行、公式、比较及组合判定 | 主映射；确有不同分支时拆分支映射，共同规则不复制 |
| 大量标准表值与完整分支条件 | 配套已核验工作簿/数据文件；表号、单位、源格和条件与主映射互相定位 |
| 标准疑点和软件补充解释 | 既有根问题台账记录唯一编号及状态，复杂解释留在标准专属档 |
| 运行时表值及业务字段元数据 | 现有 Canonical 与标准定义；能够可靠生成的内容从批准依据生成，标明来源版本 |
| 计算规则的可执行实现 | 对应标准 Calculator；明确引用所实现的映射修订与软件决定 |
| GUI/Excel/Word 的控件、列和版式 | 各自适配器；只维护位置与样式，不重新定义业务值 |

变压器保持两份核心文件：`GB20052_变压器主映射表_V2.1.md` 与 `GB20052_2024_变压器表1-35人工校对数据工作簿_V2.1.xlsx`。前者说明规则，后者承载大量条件和数值；不得只读其中一个就开发，也不因“同源”而合并、搬动或重存冻结文件。它们的历史冻结保护继续有效，当前是否可投入新增正式实现仍按本轮核实边界处理。其他复杂标准可照此分工；简单标准无须为形式多建工作簿。[依据 S5]

### 3.2 运行时不解析映射文档

批准依据与可执行实现是有来源关系的不同层。Markdown 便于审阅，校对 Excel 便于核数，Canonical/标准定义便于运行，Calculator 负责计算；这些必要形态可以并存。要消除的是相互独立维护的业务真值，不能把所有文件强行合成一个。

可确定生成的表值、名称、单位、候选项、字段说明和模板投影尽量单向生成；复杂公式仍可在专用 Calculator 中明确实现并以独立预期验证。不建设“任何标准都能解析”的通用规则语言或运行时 Markdown 引擎。

复用 `src/equipeffi/standard_manifest.json`、现有资源和 evaluator registry，在既有条目中明确标准号/版本、Profile、映射修订、数据包版本和真实计算器版本。注册事实供目录、调度与追溯读取，不另外设一份需人工同步的标准支持状态数据库。文档批准事实、运行时能力、标准生命周期分别保留含义。

## 四、目标职责与具体去重落点

### 4.1 复用现有结构，不另建一套框架

| 现有位置 | 目标职责 | 本次计划中退出的重复内容 |
|---|---|---|
| `application/dto.py`、`application/ports/` | 在既有空 DTO 入口补充最小请求/结果契约，复用现有端口 | 各端自行定义同一业务字段；再建第二套 contracts/DTO 框架 |
| `domain/evaluation/evaluator_registry.py`、`standard_manifest.json` | 注册标准实现并按完整身份选中 | 仅按设备类型覆盖条目；再启用 `domain/devices/registry.py` 成为第二注册中心 |
| `centrifugal_pump_analysis_service.py` | 保留必要泵专属输入/路由适配，将公共编排迁入统一 AnalysisService | 每接一个标准复制整份泵服务；仅改类名却保留全部泵硬编码 |
| `application/lifecycle/` 与现有记录仓储 | 复用记录模型、快照、查询、单台与批次记录规则 | 每标准一套 Record、SQLite 表或历史管理器 |
| 现有结果显示函数、字段与指标定义 | 公共结果名称和业务描述投影；用稳定字段/指标 ID 关联 | 中文标签充当数据键；GUI/Writer 分别维护限值名称与解释 |
| `src/equipeffi/composition.py` | 保留一个正式用例装配入口；旧入口逐步转换并转发 | 新旧 Application 链长期各自计算同一业务 |
| Excel Reader/Writer、未来 Word exporter、API 适配器 | 解析/校验载体，调用正式用例或读取已保存结果，再排版/传输 | 各端重新判级、重算历史结果、补造业务结论 |
| `presentation/qt/` | 公共壳和页面骨架，按标准注入必要表单与指标区域 | 每标准复制整套首页、目录、记录、设置及导出页面 |

现有正式 Qt 和 V6 Excel 已共享泵计算服务，这部分应继续复用；旧 `EvaluationService → EvaluationFacade → ApplicationApi` 与正式链之间仍有差异，因此公共用例收拢必须解决入口差异，不能只增加一个空 Protocol 就宣布完成。[依据 S1、S6]

### 4.2 最小公共输入与结果

公共请求需表达：选中的标准身份与版本、Profile 或可解析分类、按稳定字段 ID 组织的输入、必要工况及评价日期。是否必填、如何换算、能否推导、如何选表仍由相应标准定义/实现决定。

公共结果需表达：实际执行的标准身份；评价状态与等级；稳定指标 ID 对应的实测/计算值、限值和单位；原因与缺失项；记录资格；映射、数据、计算器版本及来源。十进制值在跨进程传输中使用约定的无损表达，不能中途转成浮点而损失既有精度。复用已存在的快照字段，无实际需求不改数据库结构。

设备类型不能单独标识一套规则。同一设备的不同标准、不同年份和不同 Profile 必须可同时登记、明确选中；结果和记录的标准身份从实际选中实现派生，不能照抄用户输入的标准文字。输入指纹也应纳入真正参与评价的标准/规则身份；这不改变“每次合法分析独立形成记录”的现有产品规则。

### 4.3 核心算法与平台接口

Domain 保留数值和标准判定；Application 负责调用、流程及记录协调；Infrastructure 读取标准包、Excel/Word、SQLite 和文件；客户端只经 Application 契约调用。`domain/evaluation/elimination.py` 已有条目注入接口，可把资源读取移到装配/基础设施层，避免核心依赖包路径。[依据 S7]

桌面 macOS/Linux 可以在后续复用现有语言和适配层；iOS/iPadOS、Android、鸿蒙、小程序的本地运行方式需要各自选择。当前应保留纯数据接口、无损序列化、版本信息和可移植判定向量。按锁定架构，已经声明支持的本地业务能力须能本地完成正式计算，云服务只是可选增强，不能成为核心计算必须在线的前提。后续再决定各平台采用本地嵌入还是移植数值核，以及完整版/轻量版的具体范围。现有 Android/JSONL 骨架不等于这些平台已经正式可用，也不因此必须现在保留整套旧业务算法。

## 五、UI 共用范围与保留差异

中央当前家族规格已明确：新建只统一基本信息、业务数据、数据检查、计算、结果五类功能，不强制表单、页签、步骤或业务逻辑一致。这与 Owner 本轮要求一致。下表是结构实施方向，不冻结仍在设计中的色号、尺寸、排序和表单细节。[依据 S8]

| 页面/区域 | 共用内容 | 允许保留的差异 |
|---|---|---|
| 首页与业务壳 | 无侧栏首页、业务页导航、SVG 视觉语言、底部设置及真实能力提示 | 产品名称、已开放入口和业务动作名称 |
| 标准库列表与详情 | 同一目录服务；五列列表；详情单页三个连续分区 | 每个标准的真实范围、指标、条款和限值 |
| 新建分析 | 标准上下文、基本信息区域、检查/分析动作、共享结果呈现 | 泵、变压器等不同字段组、分支选择、条件联动及复杂度 |
| 分析记录 | 搜索和全部记录可达、独立详情、两个页签、不可变结果读取 | 标准专属输入、指标和可读计算依据 |
| 表格导入 | 模板、文件、检查、处理结果四区域及错误反馈 | 各标准的 Sheet/列适配、支持能力和批次内容 |
| 设置与通用组件 | 已有路径/显示等设置、按钮、空状态、提示样式 | 确有产品需求的选项；不为凑齐菜单增加空功能 |

“共享新建页”实现为公共容器加标准专属表单片段。通常由共享字段元数据形成基础控件；复杂条件可保留该标准自己的小型表单实现。不要为了统一而建完整低代码表单引擎，也不要为每个标准复制六个页面。

三软件保持设计规则和资产语言一致，不要求现在建立跨仓 PySide6 运行时包。碳排放 UI 的未定稿设计继续作为待协调参考；执行 UI 工作时按中央当前已合并指南读取已确定项和 OPEN 项，不靠 EquipEffi 自行替三软件确定最终细节。

## 六、按五个工作包实施

以下为整改工作包，不重编号既有 Phase，不以本方案自行宣布某 Phase PASS。工作包按依赖推进，普通实现按已批准范围执行；真实标准解释、Golden 真值、冻结基线或支持范围变化仍按既有规则处理。每包用一份简短变更与验证摘要，包含被替代旧路径的处置，避免另建迁移台账和多轮长报告。

### 工作包 A：先收口语义和已复现缺陷

**目标：先防止错误来源、单位和显示关系继续传播。**

具体动作：

1. 按第二节统一共享结果投影及 Qt/Excel 直接显示位置；清理当前活跃说明与新约定的冲突，不修改数值判定和历史原始快照。
2. 修复检查报告 F01：泵请求伪填其他标准号时拒绝不匹配；结果和 Record 的身份由实际选中标准产生，指纹包含相应身份。
3. 修复 F02：V6 Reader 不能截掉换行后的单位后继续按原单位接收。用稳定字段标识、预期单位及经批准的别名检查输入；确有批准换算则执行，未支持单位明确报错，不要求整本工作簿字节哈希一致。
4. 修复 F03：阈值输出改以稳定指标 ID 读取，共享定义提供名称和单位；改“1级”文字不能令 Excel 结果列漏值。
5. 修复 F06：活动标准包缺失、损坏或无法读取时，在加载边界报系统资源错误，不能伪装成输入非法或资料不足；补足 F05 真实计算器版本，避免版本字段只有 `pump_water` 等 Profile 名。

主要文件：正式泵分析服务、`json_repository.py`、`pump_workbook_reader.py`、`pump_result_writer.py`、共享显示入口及 Qt 分析/记录页。首包只做这些问题所需的最小调整，不与大规模服务拆分混成一次提交。

### 工作包 D：退出旧资产，压缩活跃文档与重复验证

**目标：真正删掉失去职责的路径，而非只在旧代码旁增加新的公共代码。**

| 对象 | 处置规则 |
|---|---|

## 七、单人维护保留的最少验证

轻量化重点是消除重复审批、重复执行和只证明实现自己的测试；与真值、输入单位、边界和历史记录直接相关的验证仍需保留。预期必须来自批准依据，不能由新代码反推后当作独立验证。

| 改动内容 | 通常需要的验证 |
|---|---|
| 纯说明、链接、目录入口 | 修改范围、链接和事实检查；确认没有动受保护资产 |
| 结果名称、普通 UI 排版 | 共享显示映射及实际修改端的少量关键状态/操作检查 |
| 业务规则、标准数据、单位或字段语义 | 对应标准金样、边界和受影响输入/导出回归 |
| 公共用例、注册与序列化 | 标准身份不串包、已接入端同结果、无损值、历史读取与错误边界 |
| 批量容量/读取写入性能 | 与改动相关的容量样本和实测；不因文案改动重复压力测试 |
| 正式发布或打包内容 | 实际目标平台产物与启动烟测；不提前建立所有未来平台 CI |

每包摘要只回答：改了什么、为什么、依据何处、哪些旧路径已退出、验证结果及未覆盖限制。继续记录真实 pass/fail/error/skip；普通重构不重新扮演多个审批角色，不另建验收数据库、通用审计框架或新的一整套阶段门禁。
