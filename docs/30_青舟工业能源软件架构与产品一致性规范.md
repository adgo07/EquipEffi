# 青舟工业能源软件架构与产品一致性规范

**文档版本：** V1.0  
**形成日期：** 2026-09-21  
**适用对象：** 温室气体排放核算软件、设备能效分析软件、未来工业能源综合版  
**文档性质：** 当前实现盘点、产品家族共同约束与后续演进基线  

## 1. 文档目的

本文将“青舟温室气体排放核算软件”现有工程、界面、数据、计算、记录、测试和交付约束整理为一份可执行基线，用于：

1. 指导“设备能效分析软件”保持与碳排放软件一致的产品体验和基本工程架构；
2. 防止两个项目分别复制、分别修改公共外壳，最终无法低成本合并；
3. 为未来“工业能源综合版”保留清晰的模块边界；
4. 为 Windows 之外的平台保留业务规范、数据契约和测试资产，而不是强行复用桌面 UI 源码。

本规范的核心原则是：

> 统一“怎么使用、怎么组织、怎么验证”，隔离“算什么、依据什么标准、产生什么专业结论”。

## 3. 当前状态摘要

### 3.1 已实现的产品范围

当前仓库交付的是“青舟温室气体排放核算软件”Windows x64 V1.1.0，技术栈为：

- Python 3.12 x64；
- PySide6 / Qt Widgets；
- SQLite；
- PyInstaller `onedir` 便携式交付。

当前完整业务链仅覆盖：

- GB/T 32150—2025 通用规则层；
- GB/T 32151.34—2024 炭素材料生产企业核算模块。

其余七项计划标准只有目录、状态和官方来源信息，不包含计算规则。

### 3.2 当前阶段状态

代码和实施报告已记录 UIR04 实现完成并进入待验收状态，最近一次记录的全量测试为 158/158 通过，Windows standalone 构建、发布审计、归档校验及隔离启动均已执行。

但治理文档存在一处状态同步差异：`TASK_STATE.md` 顶部仍写 `UIR03_PASS`，文件后部已记录 `UIR04_READY_FOR_SOL_REVIEW`。因此在 Sol 正式验收前，不应把 UIR04 表述为已经最终通过，也不得自动启动 UIR05 或 G09。

### 3.3 当前明确没有实现的能力

- Excel 导入解析和执行；
- 报告、Word/PDF/Excel 导出和打印；
- 企业档案、企业层级、审批、多用户协作；
- `.qzproj` 项目保存、草稿和跨启动恢复；
- 云端、账号、同步和在线许可证；
- 商业安装器、代码签名和自动升级；
- 其他七项行业标准计算模块；
- 设备能效分析软件本身。

设备软件不得把这些“未来规划”误认为已经存在的公共能力。

## 4. 产品家族的边界

### 4.1 必须共用或保持一致

- 工程分层和依赖方向；
- AppShell、侧栏、品牌区、页面容器和滚动策略；
- Design Token、字体、颜色、间距、按钮、卡片、表格和状态语义；
- 首页的“开始工作 + 最近工作”结构；
- 标准库、参数库的基本查询与来源追溯思路；
- Decimal 精度策略、单位服务和稳定 ID 规则；
- Canonical Source、数据版本和迁移原则；
- Repository 数据访问边界；
- 日志脱敏、发布审计、测试分层和用户文件保护；
- 跨平台数据契约与黄金测试方式。

### 4.2 必须独立维护

- 业务对象和专业术语；
- 标准适用逻辑；
- 输入字段和字段语义；
- 计算公式、插值、判定和评价规则；
- 专业校验及错误定位；
- 结果指标和结论模型；
- 业务页面和专业详情；
- 产品自己的 Canonical 数据和业务测试案例。

设备能效软件不能复用碳核算公式、排放源模型、参数推荐规则或记录快照结构中的专业含义。可以复用的是模式和契约，不是碳业务对象本身。

## 5. 当前真实工程架构

### 5.1 依赖方向

当前目标依赖关系为：

```text
Presentation（PySide6 页面、Shell、控件）
                  │
                  ▼
Application（查询、流程编排、参数适配）
                  │
                  ▼
Domain / Standards（模型、规则、计算、校验）
                  │
                  ▼
Repository Protocol（抽象契约）
                  ▲
                  │
Infrastructure（SQLite、Canonical 构建、迁移、日志、交付）
```

强制要求：

- Domain/Core 不得导入 PySide6、sqlite3、Windows API 或页面控件；
- UI 不得承载计算公式；
- 数据查询和持久化通过 Application Service / Repository 完成；
- Infrastructure 可以依赖 Domain 契约，Domain 不得反向依赖 Infrastructure；
- 输入先按字符串接收，在边界处转换为 Decimal，不允许先经过二进制浮点数。

仓库已有自动测试扫描 `packages/core`，禁止其中出现 `PySide6`、`sqlite3`、`win32api` 和 `winreg`。

### 5.2 当前目录职责

|目录|当前职责|设备软件应如何对应|
|---|---|---|
|`apps/carbon_accounting_desktop`|应用入口、产品配置、依赖装配、路径和日志启动|建立设备产品入口，只保留设备名称、数据目录和装配代码|
|`packages/core`|Decimal、单位、通用模型、Repository、规则和参数解析基础|优先复用真正通用部分，不加入设备 UI|
|`packages/application`|查询服务和应用流程适配|设备建立自己的用例服务，共享通用接口|
|`packages/ui`|Shell、Design Token、路由、公共页面，也包含碳核算专用页面|必须进一步拆分公共 UI 与产品 UI，不能整包复制|
|`packages/standards`|标准目录读模型和 GB/T 32151.34 领域计算|设备标准和算法必须独立命名、独立测试|
|`packages/reference_data`|Canonical 校验|共享校验框架，产品 Schema 和数据分区|
|`packages/persistence`|SQLite 迁移、Catalog 构建和 Repository 实现|复用基础设施模式，数据库文件和表职责保持隔离|
|`data-source`|Canonical JSON 数据|增加设备产品分区，不把设备参数写入碳业务文件|
|`specs`|Schema 和未来跨平台业务规范入口|设备软件必须建立自己的业务规范、契约和黄金案例|
|`migrations`|三套 SQLite 迁移|按数据库职责维护，不跨产品共享业务表|
|`resources`|Logo 和 SVG 图标|共享同一公司品牌资源和图标语言|
|`tests`|分阶段单元、组件、GUI、持久化、交付测试|设备软件建立镜像测试层级，并共享公共 Shell 契约测试|
|`scripts`|Canonical、建库、构建、发布审计、冒烟|参数化为产品构建，不复制后各自漂移|

### 5.3 当前代码中尚未完全公共化的部分

以下文件虽然位于 `packages/ui`，但仍含碳核算专用语义：

- `carbon_material_page.py`；
- `field_specs.py`；
- `AppRoute.NEW_ACCOUNTING`；
- `RecentRecordViewModel` 的企业、标准、排放量字段；
- `ShellViewModel` 的“核算”“参数与因子库”等默认文案；
- 页面工厂中对核算页面和记录页面的具体装配。

因此当前仓库是“已经具备公共化基础”，不是“公共包已经可以直接供三产品无条件引用”。设备软件开发时不得复制整个 `packages/ui` 后改名，也不得直接把设备字段塞进碳核算 ViewModel。

建议在得到 Sol 批准后，将其逐步拆为：

```text
packages/ui_common/
    shell
    design_tokens
    icons
    generic routing
    generic home components
    generic status/dialog/table helpers

apps/carbon_accounting_desktop/presentation/
    carbon routes
    carbon pages
    carbon record columns

apps/equipment_efficiency_desktop/presentation/
    equipment routes
    equipment pages
    equipment record columns
```

这只是目标拆分建议；新增一级包、迁移公共接口和修改现有导入路径会影响现有软件，实施前必须作为独立阶段由 Sol 批准，并用现有 158 项测试及新增公共契约测试保护行为。

## 6. 界面一致性规范

### 6.1 公共 Shell

三个独立产品以及综合版内的对应模块应使用同一空间结构：

```text
AppShell
├─ Sidebar（固定 248 px，不滚动）
│  ├─ BrandArea（固定 120 px）
│  ├─ 公司 Logo
│  ├─ 产品名称
│  ├─ 六个连续业务入口
│  └─ SettingsEntry（底部锚定）
└─ MainContent
   ├─ 最大内容宽度 1360 px
   ├─ 页面独立纵向滚动
   └─ 禁止页面级横向滚动
```

设备能效分析软件的正式导航顺序为：

1. 首页；
2. 标准库；
3. 新建分析；
4. Excel 导入；
5. 分析记录；
6. 参数库；
7. 设置（固定在左下角，不属于连续业务流程）。

禁止增加“基础资料、业务处理、系统管理”等导航视觉分组，也不得把三个模块的所有菜单在综合版侧栏中平铺成十几项。综合版应先提供模块选择页，进入模块后继续使用对应产品的同款导航。

Windows 字体优先使用 `Microsoft YaHei UI` / `Microsoft YaHei`。页面标题 24 px、模块标题 18 px、卡片标题 16 px、正文和表格 14 px、辅助文字 13 px。

### 6.3 首页

首页定位为专业工具起始工作台，不是 KPI Dashboard。公共结构为：

```text
WorkbenchHome
├─ HomeHeader
├─ PrimaryWorkspace
│  ├─ StartPanel（约 320 px）
│  └─ RecentWork（剩余宽度）
├─ RecentStandards（预留）
└─ StatusSummary（一行弱信息）
```

设备软件 StartPanel 顺序固定为：

1. `＋ 新建分析`，主操作；
2. `Excel 导入（暂未开放）`，禁用预留；
3. `查看标准库`，普通操作。

设备最近记录建议字段为：分析对象、设备类型、关键指标、分析结论、分析时间、操作。不同设备不得被强制转换为同一个指标；可通过动态“关键指标 + 分析结论”展示。首页记录不得横向滚动。

禁止在首页加入三张巨大 KPI 卡、排行、饼图、趋势图、GIS、新闻、AI 对话、审批、日历或资产管理。

### 6.4 业务页面

公共一致性不等于业务页面像素级相同。设备页面可以采用适合设备分析的表单、曲线、工况表和结果区，但必须遵守：

- 页面标题、卡片、按钮、表格、状态提示和专业详情使用公共组件；
- 普通路径使用业务中文，不显示内部 ID、变量名和开发术语；
- 专业参数、条款、来源、插值过程和稳定 ID 放入按需“专业详情”；
- 输入控件由字段定义驱动，单位不可让用户自由填写；
- 立即拦截非法数字、负值和超范围比例；
- 页面只派生展示状态，不发明新的 Domain 状态；
- UI 校验只负责格式和即时反馈，专业合法性仍由 Domain 判定；
- 复杂页面允许纵向滚动，禁止为了塞进一屏压缩文字和控件。

碳软件的 `FieldSpec + typed_inputs + SourceCard` 是可借鉴模式，但碳字段定义本身不可复用。设备软件应建立 `EquipmentFieldSpec` 或等价产品定义，其中至少包含稳定键、显示名、数据类型、单位、范围、必填性、帮助文字、标准条款、来源定位和高级字段标记。

### 6.5 Excel 入口

当前产品家族统一保留 Excel 导航和占位页，但内部控件全部禁用、不可聚焦，不得伪造导入进度或成功结果。未来启用时，Excel 数据必须转换为与人工输入相同的结构化 Domain Input，并调用同一个计算引擎，禁止建立第二套 Excel 专用算法。

## 7. 领域、计算和校验规范

### 7.1 DecimalPolicy

当前实现使用至少 28 位、实际默认 40 位有效数字的 Decimal 上下文，默认显示 2 位，舍入方式为 `ROUND_HALF_UP`。规则为：

- 接收字符串、Decimal 或整数；
- 拒绝 float 和 bool；
- 中间结果不舍入，除非标准明确要求；
- 持久化未舍入值；
- 显示层才按统一策略格式化；
- 标准专属舍入规则必须版本化并进入测试。

设备效率、能耗、流量、扬程、功率、负荷率和插值结果同样不得在页面中直接使用 `round()` 或语言默认浮点行为。

### 7.2 UnitService

单位使用稳定 `unit_id`，显示符号不是主键。换算集中在 UnitService，算法中不得散落 `÷1000`、`×3600` 等魔法常数。

设备软件应在同一机制上扩展设备领域所需量纲，例如功率、压力、流量、温度、转速和效率。新增单位必须声明量纲、基准因子、别名和往返测试；不能仅在下拉框中增加文本。

### 7.3 稳定 ID 和版本

标准、参数、因子、公式、规则、记录和来源均使用稳定 ID。显示中文可以变化，稳定 ID 不得使用页面标签代替。

至少区分：

- `app_version`；
- `schema_version`；
- `data_version`；
- `formula_version` / `algorithm_version`；
- 标准版本和来源版本。

### 7.4 校验等级

统一使用：

- `ERROR`：阻止成功计算和记录生成；
- `WARNING`：允许生成 `COMPLETED_WITH_WARNINGS`；
- `INFO`：说明默认值、插值或辅助过程。

Presentation 可以把稳定错误码翻译成业务中文并定位到相应卡片，但不得复制或改写 Domain 校验规则。原始稳定码和专业信息可在专业详情中保留以便审计。

## 8. Canonical 数据与数据库

### 8.1 Canonical Source

标准、参数和参考数据的唯一事实源必须是可校验的 JSON/YAML。当前实际采用 JSON：

```text
data-source/carbon_accounting/catalog.json
        ↓ schema + cross validation
        ↓ stable sort / normalization
build/databases/catalog.sqlite
```

SQLite 是 Windows 的查询和部署格式，不是编辑事实源。设备软件应建立独立的 `data-source/equipment_efficiency/` 和相应 Schema/交叉校验，不得直接手工维护发布用 SQLite。

每个正式参数至少需要：稳定 ID、值、单位、来源、条款或表格定位、版本/年份、有效期、适用范围、审核状态和备注。不得依据记忆、搜索摘要或示例值录入。

### 8.2 三库职责

当前碳软件已经定义并可初始化三套物理数据库：

```text
catalog.sqlite
    官方标准、来源、参数、因子、版本

user.sqlite
    用户设置和本地偏好

records.sqlite
    成功记录、输入/结果/参数快照、规则快照、审计日志
```

其中 `catalog.sqlite` 和 `records.sqlite` 已进入当前运行链；`user.sqlite` 已有独立迁移和初始化能力，但当前 V1.1.0 的设置功能仍很轻量，不能据此宣称完整的用户偏好持久化已经交付。

设备软件应保持相同职责拆分，但使用自己的产品数据目录和业务表，不得为了未来综合版提前让三个独立软件共用一个 `all.sqlite`。

综合版可以通过模块级 Repository 或查询聚合展示跨模块入口；不应通过混放业务表获得“统一”。

### 8.3 迁移

- 每个数据库独立维护 migration；
- 迁移只向前应用；
- 未知未来版本安全失败；
- 初始化必须幂等；
- 失败不得删除或覆盖用户库；
- Schema 变化必须与应用版本和数据版本分开记录。

## 9. 记录、快照与审计

当前碳软件采用“计算成功即生成不可编辑记录”：

1. Presentation 收集并转换输入；
2. Domain 执行完整校验和计算；
3. 任一 ERROR 阻止成功结果；
4. 成功后在单一事务中写入记录和 CREATE 审计；
5. 保存输入、计算结果、参数值、来源、规则和算法版本快照；
6. 再次计算创建新记录，不覆盖历史；
7. 删除采用逻辑删除，同时写 DELETE 审计。

设备分析若采用“分析即归档”的同类工作流，应保持上述不可变和快照原则。若设备产品确实需要可编辑项目、工况草稿或反复调参，则属于不同生命周期，必须在设备业务规范中显式定义，不能偷用碳软件记录模型，也不能为了界面一致强行取消设备业务需要。

长期公共原则是：历史结果不能因为当前参数库、标准或算法升级而自动漂移。

## 10. Repository 与可替换基础设施

当前核心契约包括 Standard、Parameter、Record、Settings 和 Rule Repository。设备软件应通过接口依赖：

```text
Application / Domain
        ↓
Repository Protocol
        ↓
SQLite Repository（Windows）
```

未来平台可以替换为本地数据库或 API Repository，而不改变业务服务。测试优先使用内存假实现，不应为了测试启动真实 UI 或依赖固定磁盘路径。

## 11. 日志、安全和版权

- 日志采用结构化 JSON Lines；
- 默认不得记录企业敏感数据、完整活动数据、报告正文、许可证或密钥；
- 标准全文不得打包进软件；
- “打开标准原文”只能打开已核验的官方网址；
- 发布包不得含 `计算表/`、测试数据库、开发目录、环境文件、密钥或用户数据；
- `计算表/` 是用户参考文件，任何任务均不得修改、删除或覆盖；
- 删除业务记录必须二次确认并留下审计证据；
- 外部输入和 Canonical 数据在进入 Domain 前均须验证。

设备标准同样适用上述版权和来源要求。

## 12. 测试与质量门禁

### 12.1 测试层级

- L1：当前函数、类、迁移或组件的最小测试；
- L2：当前工作包相关模块回归；
- L3：阶段验收和全量回归。

测试报告必须记录命令、环境、通过、失败、错误、跳过以及未执行原因，不能只写“测试通过”。

### 12.2 每个产品都应具备的测试

- Domain 无 UI/SQLite/Windows 依赖扫描；
- Decimal 边界和舍入；
- 单位兼容、换算与往返；
- 稳定 ID、枚举和不可变模型；
- Repository 内存假实现与 SQLite 实现契约；
- Canonical Schema、交叉引用、重复 ID、来源和单位校验；
- 数据库首次创建、重复初始化、迁移和未来版本失败；
- Shell 导航顺序、尺寸、Logo、滚动和空状态；
- 输入类型、粘贴、比例转换和专业校验；
- 同一输入的 Domain parity；
- 历史快照不受当前 Catalog 变化影响；
- 记录事务、回滚、逻辑删除和审计；
- 发布包敏感文件审计和 standalone 冒烟。

### 12.3 公共契约测试

建议建立一套供三个产品共同执行的 Shell Contract Tests，以配置方式验证：

- 248 px 侧栏和 120 px 品牌区；
- 六个业务入口的固定顺序及设置底部锚定；
- 首页三个动作的顺序和权重；
- Excel 占位控件全部禁用且不可聚焦；
- 1180×720 最低窗口和 24/32 px 页面边距；
- 主内容无页面级横向滚动；
- Logo 等比例缩放；
- Design Token 未被页面硬编码绕过。

## 13. 设备能效分析软件的落地要求

### 13.1 开工前必须先冻结

1. 设备产品业务范围和首个完整设备类型；
2. 适用标准及原始来源；
3. 输入、输出、判定、插值和异常规则；
4. 设备分析结果生命周期：即时记录还是可编辑项目；
5. 参数库的 Canonical 字段和版本策略；
6. 首批平台无关测试案例；
7. 与碳软件共享代码的边界和发布方式。

### 13.2 建议工程骨架

在最终 Monorepo 决策批准后，建议形成：

```text
apps/
├─ carbon_accounting_desktop/
└─ equipment_efficiency_desktop/

packages/
├─ core/                 # 真正通用 Decimal、单位、基础契约
├─ ui_common/            # Shell、Token、公共组件
├─ reference_data/       # Canonical 校验框架
├─ persistence/          # 通用迁移与适配器基础
└─ audit/                # 公共审计基础

domains/ 或产品包/
├─ carbon_accounting/
└─ equipment_efficiency/

specs/
├─ common/
├─ carbon_accounting/
└─ equipment_efficiency/

data-source/
├─ common/
├─ carbon_accounting/
└─ equipment_efficiency/
```

目录名称不是本文件单方面冻结的接口；重点是公共能力和产品业务必须物理、命名和测试上可区分。

### 13.3 设备产品配置示例

设备产品只应通过配置改变公共 Shell：

```text
product_name          = 设备能效分析
home_title            = 设备能效分析
home_description      = 依据现行设备能效及相关技术标准开展设备性能计算与能效分析
primary_action        = ＋ 新建分析
recent_work_title     = 最近分析记录
database_name         = 参数库
record_route_label    = 分析记录
```

公共 Shell 不应通过 `if product == equipment` 累积产品分支；产品差异通过配置、页面工厂和依赖注入进入。

### 13.4 设备业务中尤其需要避免的问题

- 把所有设备强制成同一套输入和同一个“效率”结果；
- 为界面统一而复用碳核算的 AccountingInput、排放源或参数快照语义；
- 在 Qt 控件事件中写效率公式或插值表；
- 使用 float 计算效率、负荷率和曲线插值；
- 把设备参数直接写死在页面或 SQLite；
- 仅保存参数 ID，不保存本次实际使用值和来源；
- 为未来综合版让碳和设备共用业务数据库；
- 复制公共 Shell 后在两个仓库分别维护。

## 14. 未来综合版合并策略

综合版应是“一个产品入口 + 三个受控业务模块”，不是把三个应用窗口和菜单粗暴拼接。

建议结构：

```text
Suite Launcher / Module Selector
├─ 单位产品能耗模块
├─ 设备能效模块
└─ 温室气体核算模块

每个模块进入后：
公共 Shell + 模块配置 + 模块业务页面 + 模块 Repository
```

合并前必须做到：

1. 公共组件只有一个权威实现；
2. 三个产品可独立构建和运行；
3. 产品 Domain 无相互导入；
4. 数据目录和数据库职责清楚；
5. 记录 ID、标准 ID 和参数 ID 有产品命名空间或全局稳定规则；
6. 公共升级不会静默改变历史业务结果；
7. 综合版只负责模块发现、公共设置和公共能力装配，不接管专业算法。

## 15. 多平台策略

### 15.1 共享业务真相，不强求共享 UI 源码

未来 Windows、HarmonyOS、平板、小程序和 Web 应共享：

- 业务规范；
- 数据契约；
- Canonical 标准与参数源；
- 稳定 ID 和版本语义；
- Decimal 和舍入规则；
- 单位定义；
- 平台无关黄金测试案例；
- 结果和快照的语义。

可以不同：

- 页面布局和导航；
- 表格或卡片形式；
- 现场采集流程；
- 报告查看方式；
- 本地数据库或 API 实现；
- 具体编程语言。

### 15.2 当前代码中的平台边界

以下内容应留在 Windows 应用边缘：

- PySide6；
- `%LOCALAPPDATA%` 路径；
- `sys.frozen` 和 PyInstaller 资源定位；
- Windows 默认浏览器调用；
- 桌面窗口尺寸和 DPI；
- SQLite 具体 SQL。

Domain、业务规范、Canonical Schema 和黄金案例不得依赖这些内容。

### 15.3 跨平台前的必要补强

当前仓库还没有完整的企业真实黄金算例集。未来开始第二平台前，必须先建立平台无关案例文件，明确输入、参数版本、公式版本、问题等级、未舍入结果和显示结果。不同语言实现以“同一输入得到同一业务结果”为验收标准，不以共用 Python 源码为目标。

## 16. 当前技术债与决策点

以下事项应进入后续架构决策，而不是由设备项目自行处理：

1. 从 `packages/ui` 抽取真正公共的 UI 包；
2. 将碳专用 `AppRoute` 和最近记录 ViewModel 泛化为产品配置；
3. 公共 UnitService 如何扩展设备量纲又不破坏既有单位 ID；
4. 三产品最终使用一个 Monorepo，还是先以公共包版本化共享；
5. 设备分析记录是否采用不可变记录，或需要平台无关项目/草稿模型；
6. `.qzproj`、`.qzpack`、备份、授权和报告何时进入正式范围；
7. 综合版数据库是物理分库、模块子目录还是统一查询层；
8. 黄金案例的文件 Schema、版本和签审流程；
9. 公共组件 API 的兼容策略与弃用周期。

其中任何一项会改变公共接口、一级模块、数据模型或既有碳软件行为时，必须按 `AGENTS.md` 的 BLOCKED/决策流程处理。

## 17. 一致性验收清单

设备能效分析软件每个阶段至少核对：

### 工程

- [ ] Presentation、Application、Domain、Infrastructure 分离；
- [ ] Domain 无 PySide6、SQLite、Windows API；
- [ ] Repository 契约可用内存实现测试；
- [ ] 业务算法未写入页面事件；
- [ ] 公共包没有导入设备或碳专用 Domain。

### 界面

- [ ] 使用同一 Logo、字体、颜色和 Design Token；
- [ ] 侧栏 248 px，品牌区 120 px，设置底部锚定；
- [ ] 导航顺序为首页、标准库、新建分析、Excel 导入、分析记录、参数库；
- [ ] 首页为开始工作 + 最近分析，不是 KPI Dashboard；
- [ ] Excel 占位真实禁用；
- [ ] 1366×768、1920×1080、2560×1440 可用；
- [ ] Windows 100%、125%、150% DPI 无文字裁切；
- [ ] 普通页面无横向滚动，复杂内容可纵向滚动。

### 数据与算法

- [ ] Canonical JSON/YAML 是唯一事实源；
- [ ] 每个正式参数均可追溯到原始来源；
- [ ] Decimal、舍入和单位换算集中管理；
- [ ] 公式、标准、参数和数据版本分离；
- [ ] 历史结果保存本次实际使用值和规则快照；
- [ ] ERROR 阻止成功结果；
- [ ] 没有使用搜索摘要、示例值或猜测值填充正式数据。

### 测试与交付

- [ ] L1/L2/L3 命令和数量真实记录；
- [ ] Canonical、迁移、全量测试、compileall 和依赖检查通过；
- [ ] 公共 Shell 契约测试通过；
- [ ] 平台无关业务案例通过；
- [ ] 发布包不含源码资料、标准全文、测试库、用户数据和密钥；
- [ ] 用户参考文件未修改。

## 18. 结论

设备能效分析软件应与碳排放软件共享产品家族的外壳、视觉语言、工程纪律、数据治理、精度单位、Repository、审计和测试方法；不应共享或套用碳核算的专业模型、公式和页面语义。

未来合并成功的关键不是现在把两个软件写进同一个窗口，而是从一开始保证：

> 公共能力只有一个权威实现，产品业务各自独立；业务规范、Canonical 数据和测试案例比客户端技术更稳定。

按此原则实施，Windows 两个独立产品可以保持一致体验，未来综合版可以按模块装配，其他平台也可以在不重做标准研究和业务定义的前提下重新实现合适的客户端。
