# 标准原文、问题与专业解释：仓库长期归档入口

> 适用于EquipEffi后续所有设备类型与标准。**一个根问题台账＋各标准的Mapping/解释档**，轻量维护，不新增CI、数据库或双重审批。

## 文件分工（权威层次）

|类别|长期落点|用于回答|权威属性|
|---|---|---|---|
|原标准PDF及扫描图|合法持有的原件/标准来源与SHA256定位|标准实际写什么？|最高标准事实证据|
|完整标准映射表| `docs/standards/<standard_key>/` |表路由、字段、计算、适用范围、原表值及来源|经审核的标准数字化映射，不能悄悄改原文|
|**全仓唯一正式问题台账**|`STANDARD_ISSUES_REGISTER.md`（根目录）|哪些问题、唯一编号、当前OPEN/PROVISIONAL/RESOLVED？|**唯一问题ID/状态权威**|
|每项标准专业解释/软件决策|`docs/standards/<standard_key>/..._STANDARD_INTERPRETATIONS.md`|疑点怎么发现、为什么这样理解、Owner何时决定、哪些仍缺依据？|解释与过程长期留档，不另建状态权威|
|审计/校对及变更记录|对应标准目录的AUDIT/CHANGELOG/ACCEPTANCE|原始数字/分组修了什么，验收到什么程度？|证据与验收报告，不能代替标准PDF|

## 发现问题时最小流程（每次仅处理实际遇到的项）

1. **原文先行**：找到标准版本、章/条/表/印刷页与PDF物理页。合并单元格/重复行/貌似空白时查看PDF图像。不得把OCR、旧JSON、旧Excel平铺当作唯一原文证据。
2. **复用或新增稳定编号**：检索根目录`STANDARD_ISSUES_REGISTER.md`，相同问题只补已有编号；新问题按`EQP-STD-<标准号>-NNN`递增。根台账记录标准事实、技术判断、Owner软件决定、状态、影响链。
3. **复杂问题才写解释档**：按`_STANDARD_INTERPRETATIONS_TEMPLATE.md`记录歧义、对照证据、技术解释、例子、反例和明确的未决条件。简单、明确的文义直接写根台账即可，不为记录而制造材料。
4. **问题关闭边界**：`RESOLVED`可以是【有源事实】或【Owner已批准的软件实现口径】，必须清楚注明何者；`PROVISIONAL`是有工程方案但来源/适用性未证实；`OPEN`是尚未解决。不得让“软件决定”变成“标准发布机构已解释”。
5. **检查影响**：解释可能改变适用范围、阈值、阻抗分组、插值、温度、状态、Golden时，检查Mapping、数据审计、CHANGELOG、金样/测试与已有实现；无用户授权的纯文档阶段**不改生产代码/JSON/SQLite/Golden**。
6. **长效维护**：每次新增一个标准或发现疑点，执行者先读本入口＋AGENTS§7；继续现有主分支/PR流程，不额外建立“再审批一遍”的门禁。仓库根台账永远保留已失效解释编号和修改原因。

## 当前标准示例

- `gb20052_v21/`：GB 20052—2024变压器映射与审计档案。
  - 后续功能开发共同基准：`GB20052_变压器主映射表_V2.1.md`（规则总依据）与`GB20052_2024_变压器表1-35人工校对数据工作簿_V2.1.xlsx`（表值/分支校对工作底稿）。
  - 标准PDF始终是原文最高依据；V1.11“变压器标准”sheet仅供差异参考，D-08全表数据复核仍OPEN。
  - 档案内容包括表1合并单元格纠错、短路阻抗、特殊容量、B/F/H及参考温度等记录。
- 其他标准按需要建立自己的目录；**不因目录存在而自动表示该标准已SUPPORTED**。
